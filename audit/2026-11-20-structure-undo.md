## 一、结构撤销（已实现）

### 设计

`History` 新增两个方法：

```js
beginStructure(doc)          // 拍「操作前」的树形态
commitStructure(pending, label)  // 拍「操作后」，若无变化则丢弃
```

记录内容（`captureTree()`）：节点引用、父节点、层内索引、名称、可见性、
不透明度、混合模式、展开状态、蒙版引用，外加 `selected` / `activeLeaf` / `maskMode`。

**关键设计**：节点对象按**引用**保存，不复制像素。删除只是把节点从
`children` 移除，对象本身仍在，撤销时挂回去即可完整恢复内容。

### 覆盖范围

`main.js` 中已接入 9 处：

| 操作 | 位置 |
|---|---|
| 新建蒙版 | `main.js:1470` |
| 重命名 | `main.js:1519` |
| 删除图层 | `main.js:1722` |
| 不透明度 | `main.js:1742`（300ms 静默期合并） |
| 混合模式 | `main.js:1780` |
| 图层重排 | `main.js:1930` |
| 新建图层 | `main.js:1948` |
| 新建组 | `main.js:1955` |

### 实测

**新建图层 → 撤销 → 重做**：

```

撤销后  ["背景"]           ✅

```

**删除图层 → 撤销**（图层有像素内容）：

```

撤销后 2 层，墨点数 90000   ✅ 像素完好

```

```
→ 删除该图层（结构记录）

```

## 二、发现的问题：结构记录不参与淘汰

### 位置

`src/core/history.js` `commitStructure()`：

```js
bytes: 0,          // 结构记录只存引用与属性，不计入像素内存上限
```

而 `trim()` 的入口条件是：

```js
trim() {
  if (this.bytes <= this.limit) return;   // ← 这里
```

### 后果

**纯结构操作时 `bytes` 恒为 0，`trim()` 直接返回，记录永不淘汰。**

实测：连续 100 次新建图层 →

```
stackLen: 100
bytes: 0
overLimit: false        ← 永远不会触发淘汰
structCount: 100
```

连续 500 次改不透明度 →

```
stackLen: 500
bytes: 0
structCount: 500
```

### 严重程度：低

实测内存影响很小：

| 场景 | 堆内存 |
|---|---|
| 500 次结构操作 | 2MB → 2MB（无明显增长） |
| 80 次「新建 + 画 + 删除」循环 | 2MB → 2MB |

原因：结构记录只存引用和少量属性，不复制像素。
500 条记录总引用数 549 个对象，都是轻量节点。

**不是紧急 bug，但是设计缺口**：上限形同虚设，长期使用会持续持有
已删除图层的节点对象，使其无法被 GC 回收。

### 建议修法

给结构记录加**条数上限**，而不是字节上限：

```js
commitStructure(pending, label = '') {
  // ……
  this.stack.push({ kind: 'structure', …… });

  /* 结构记录不计字节，需要单独按条数限制。
   * 否则纯结构操作时 bytes 恒为 0，trim() 永不触发。 */
  const MAX_STRUCT = 200;
  let n = 0;
  for (let i = this.stack.length - 1; i >= 0; i--) {
    if (this.stack[i].kind === 'structure' && ++n > MAX_STRUCT) {
      this.stack.splice(i, 1);
      if (this.index > i) this.index--;
      break;
    }
  }
}
```

或者更简单：给结构记录一个估算字节数（如 `nodes.length * 200`），
让它参与现有的 `trim()` 逻辑。
