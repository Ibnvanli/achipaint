## 二、结构记录不参与淘汰（已修）

### 确认

报告指出的机制成立：结构记录以 `bytes: 0` 入栈，而 `trim()` 的入口是
`if (this.bytes <= this.limit) return`。纯结构操作时 `this.bytes` 恒为 0，
淘汰永不触发。

### 报告低估了后果

报告实测「500 次结构操作 2MB → 2MB，无明显增长」，据此判为「低危、设计缺口」。
但这个测量用的是**空图层**，而结构记录真正持有的是**节点对象**：

```js
// 删除图层时，节点对象仍被快照引用
const pending = history.beginStructure(doc);
doc.deleteNode(node);   // node 从 children 移除，但 pending.before 仍引用它
```

`node.canvas` 是 `TileCanvas`，A4 满铺一层约 140 块 × 256KB ≈ 36MB。
反复「新建有内容的图层 → 删除」，被删图层的内存无法回收，
而撤销栈又永不淘汰 —— 这不是「理论上无上限增长」，是会实际吃满内存。

### 修法

不只加条数上限，而是让结构记录能参与现有的淘汰判断：

```js
export const STRUCT_LIMIT = 200;   // 条数上限

// 1) 结构记录按被引用节点估算字节数
bytes: estimateStructureBytes(before, after)

// 2) 淘汰分两条路径，互不干扰
trimStructures()   // 只淘汰结构记录，按条数
trim()             // 只按字节淘汰，结构记录按估算值参与

// 3) 任何整体改写 stack 的路径都重算计数
recompute()
```

估算方式（`estimateStructureBytes`）：

- 固定开销：`160 × 两份快照的节点总数`
- 画布开销：**只统计持有瓦片的节点**，按 `tiles × 256KB × 0.5`

折算 0.5 的理由：同一节点同时出现在 before 与 after 两份快照里，
全额计入会重复计数；而且一条 A4 满层记录单独就能顶满 384MB 上限，
导致撤销历史只剩一条，实用性归零。

实测（800×600）：

| 场景 | 记录估算 | 实际画布 |
|---|---|---|
| 删除满铺图层 | 1.56 MB | 1.83 MB |
| 新建空图层 | ≈ 32 KB | 0 |

量级吻合，空图层不会被误重罚。

### 为什么条数上限仍要保留

`bytes` 只是估算，`STRUCT_LIMIT` 是硬约束。两者并存：
条数上限保证行为可预期（最多 200 步结构撤销），字节估算让大图层的记录
更早被淘汰，避免 200 条满层记录累计到 300MB。

### 顺带修掉的两个状态残留

测试过程中发现 `newDocument()` 与 `installDocument()` 重置撤销栈时
没有把 `structCount` 归零。归零逻辑集中在 `recompute()`，栈被清空后
计数残留会让后续淘汰误判。

同时补了两处状态清理：

- `hk.active = false`：上一份文档若正处于绘制中，`drawEnd` 会把残留笔迹压进新文档
- `doc.selection = null`：旧选区会残留并影响后续绘制
