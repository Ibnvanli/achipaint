## 审查前必须做的三件事

这三条是踩过坑之后加的，每条都对应一次真实的误判。

### 1. 确认基线版本，不要用旧印象

动手前先执行：

```bash
git log --oneline -5      # 现在到哪个提交了
git status --short        # 有没有未提交的改动
```

**踩坑记录**：审查 `2026-11-20-structure-undo.md` 时报告称
「hokusai 无销毁路径、变换与蒙版不同步、IPC 无白名单」三项仍未实现，
实际这三项在当时的工作区里都已补上。原因是读了数小时前的代码状态就下了结论。

代码是多个窗口并行改的，**「我上次看到」不等于「现在是这样」**。

### 2. 测量样本要覆盖真实场景

**踩坑记录**：判断「结构记录不参与淘汰」的严重程度时，
用 500 次空图层操作测出「2MB → 2MB，无明显增长」，据此判为低危。
但结构记录真正持有的是**节点对象**，`node.canvas` 是 `TileCanvas`，
A4 满铺一层约 36MB。反复「新建有内容的图层 → 删除」才会暴露问题。

**空对象测不出重量**。测内存要构造尽可能接近真实使用的样本。

### 3. 报告写完，回头验证引用的行号

```bash
# 逐个核对报告里提到的位置
sed -n '1415p' src/main.js
sed -n '29p' src/platform/fileio.js
```

**踩坑记录**：首份审计写「`dispose()` 定义了但从不调用」，
实际该类根本没有 `dispose()` 方法，109/113 行的 `free()` 在
`ensureSurface()` 内，是画布尺寸变化时的重建逻辑。

写的时候觉得对，核一遍就露馅。**行号是最容易记错的部分。**
